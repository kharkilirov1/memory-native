# mx6 gap decomposition on a held-out split (G4) - 2026-10-31

Raw evidence (unedited logs from the Colab G4 sessions): `mx6_g4_decomp_2026_10_31/`
- `heldout/` - held-out harness: dense, mx6 (e8m0 / nvfp4 / ladder-headroom / lr probes), `tern_counter` lr sweep.
- `decomposition/` - dense_nobias, dense_rms, qat_*, na_wd, na_slr, na_fp4 (C = 4 / 8 / 16).
- `memorization_superseded/` - the earlier 6000-step runs on the OLD harness (validation == training data). Kept for the record, **superseded**.

Every number below is copied from those logs, or derived from them (marked "derived" or "(c)").
Statements are labelled **[verified]** (read off the logs or the code) or **[hypothesis]** (not tested by these runs).
The standard deviation is the sample sd (n-1), the convention the logs use (reproduced on the dense row: 0.0108).

## TL;DR

1. **[verified]** The `e1_quality` harness had no held-out split: "val" was measured on the training text. All earlier
   quality numbers (E1 report, the quality/rescale tables in `mx6_g4_2026_10_31.md`, the g4b 6000-step runs) measure
   memorisation. Fixed in the harness (`--val-frac 0.1` default). Use only the numbers in this report.
2. **[verified]** Held-out, d=128, 6000 steps, cosine: dense 2.286 | qat_fp4 2.298 | na_fp4_c8 2.361 @ 8.69 bits |
   tern_counter 2.481 @ 6.56 bits | mx6 e2m1_c5 (nvfp4) 2.547 @ 6.69 bits.
3. **[verified]** The RMS-normalised, momentum-free update costs nothing on a dense model (dense_rms 2.270 vs dense_nobias 2.289).
4. **[verified]** Most of the mx6 gap is the FORMAT chosen to fit a 6-bit word, not the counter: with an fp32 latent,
   full E2M1 costs about 0.01, the reduced `{0, .5, 1, 6}` ladder +0.14, ternary +0.14..0.16.
5. **[verified]** The counter itself costs +0.05 (ternary), +0.12 (e2m1 ladder), +0.06 (full fp4, C=8); it shrinks
   with C (fp4: +0.14 at C=4 -> +0.06 at C=8). Best counter arm: `na_fp4_c8`, +0.07 vs dense.
6. **[verified]** Counter weight decay and learnable scale (as implemented then) did not help; C=16 on the fp4 ladder
   collapsed because the code overflows its storage type.
7. **[hypothesis]** `na_fp4_c8` weights are U-shaped while `qat_fp4` weights are bell-shaped: a frozen / ceilinged block
   scale. Next experiment, not yet run.

in those tables are unvalidated as well.

**(b) The RMS-normalised, momentum-free update costs nothing. [verified]** `dense_rms` at lr 1e-2: 2.2702 +- 0.0070 vs
`dense_nobias` 2.2891 +- 0.0039. Caveat: AdamW was run at one lr only (0.003, not swept) while the RMS step had three, so
read this as "no cost", not "RMS beats AdamW". It also fits the train-fits-better, gap-larger pattern (train 1.8862 vs 1.9208,
gap +0.384 vs +0.368). At lr 3e-2 one seed degrades (2.4849; its curve sits near 3.5 until step 2500).

**(c) Format cost: full E2M1 is nearly free, the 6-bit-word ladder is not. [verified numbers; the causal reading is derived]**
With an fp32 latent and AdamW: full E2M1 +0.009, `{0,.5,1,6}` +0.140, ternary +0.142..0.157. A 6-bit code word has 64 codes;
`{0,.5,1,6}` has 7 signed values x 9 accumulator levels (C=5) = 63, so it fits. Full E2M1 has 15 signed values, which leaves
at most 4 accumulator levels in 6 bits (C <= 2, derived), i.e. no usable counter. The 6-bit budget therefore forced a ladder
that throws away what FP4 is good at, and that costs 0.14 before any counter is involved. `qat_fp4` is also lr-sensitive:
at 1e-2 it gives 2.4450 with sd 0.1344 (seeds 2.5382 / 2.3422 / 2.3177 / 2.5819).

**(d) Counter cost is moderate and shrinks with C; the best counter arm is full-fp4 C=8. [verified, 2 seeds for fp4]**
`na_fp4_c8` 2.3607 (8.69 bits) is +0.07 vs dense and beats `tern_counter` 2.4811 (6.56 bits) by 0.120 for +2.13 bits (derived).
On the fp4 ladder the counter cost halves from C=4 (+0.138) to C=8 (+0.062). The 6-bit `na_e2m1_c5` nvfp4 (2.5474) is 0.066
worse than the lr-tuned `tern_counter` at similar bits (derived), with mx6 lr not tuned downward (see Limits). nvfp4 scale vs
e8m0 on `na_e2m1_c5`: 2.5474 vs 2.6036 (-0.056, 3 seeds each, +0.25 bits, derived).

**(e) Counter weight decay and learnable block scale did not help (as implemented then). [verified, 2 seeds]** Against the same
seeds 0-1 baseline (2.5449): wd 0.001 +0.020, wd 0.003 +0.026, wd 0.01 +0.185 (kurt 7.97, 22 % zeros); scale-lr 3e-3 +0.040,
1e-2 +0.063 (clip 1.63 %); scale-lr costs +0.19 bits (6.876 vs 6.688, derived). A learnable scale cannot grow a block already
at E4M3 byte 126 (= 448): the snapshot's `packed_na.py:334` says `rebase_tscale` is the only headroom, so (e) does not test the
ceiling hypothesis in (f).

**(f) `na_fp4_c8` weights are U-shaped; `qat_fp4` weights are bell-shaped. [verified shape; the cause is a hypothesis]**
Deployed-weight kurtosis 1.66 (C=8) / 1.94 (C=4) vs 3.07 for `qat_fp4` (Gaussian 3, uniform 1.8); exact zeros 2.3 % / 3.2 % vs 6.9 %;
seed 0: 35.5 % of C=8 weights on the two outer rungs (+-6: 17.7 + 17.8 %). The block scale was frozen in every run here **[verified]**:
`grown=0` on every log line (`scale_growth` is off by default; the auto-rebase in `layer.py:656-659` of the snapshot runs only under
`scale_growth="pressure"`), and `scale_moves` is non-zero only in the `na_slr` runs. **Hypothesis:** with a frozen scale the weights that
grow have nowhere to go but the top rung, and nvfp4 initialisation puts the largest block at E4M3 byte 126 so the scale cannot
grow without `rebase_tscale` (session note; code: snapshot `packed_na.py:297,334`). Not tested: no scale-byte statistic is logged.
**Next experiment:** on `na_fp4_c8` log the block-byte histogram and the share of blocks at byte 126, then run with
`--scale-growth pressure` (and/or a lower initial headroom) and compare the weight histogram and val against `qat_fp4`.

**(g) Code overflow at C=16. [verified: code + log; not isolated by an ablation]** For the fp4 ladder n_codes = 15 values x
(2C-1) accumulator levels: 105 (C=4), 225 (C=8), 465 (C=16). The harness prints `bits = ceil(log2 n_codes)` (9 -> 9.688), but codes are
cast to `torch.uint8` in the Colab snapshot (`g4d/mx.tar`, `mx6/packed_na.py:190,287,404,415`; no `code_dtype` / `MAX_CODES` there),
465 > 256, so a code above 255 would wrap. The C=16 log has no positive rung at all in the seed-0 histogram (`-6` 57.0 %) and
val 3.1171. That the wrap is THE cause was not isolated by an ablation. Derived: with a uint8 code the largest C for a 15-value
ladder is 9 (15 x 17 = 255). The pre-hook "measured == expected bits" passed because it checks the ideal bit count, not the
storage width. The working tree (uncommitted, edited after these runs by another agent; not run on GPU by me) now has
`PackedNA.code_dtype` (int16 beyond 256 codes) and a `MAX_CODES` ValueError guard in `PackedNA.__init__`.

**(h) The `tern_counter` optimum lr here is 3e-2, 10x the `cli.py` default 3e-3. [verified]** 2.6479 (sd 0.0495, seed 3 = 2.7200)
at 3e-3; 2.5479 at 1e-2; **2.4811** at 3e-2; 2.5584 at 1e-1; 2.8176 at 3e-1 (half-decade grid). Moving from the default to
3e-2 gains 0.167. Any earlier `tern_counter` comparison at the default lr is under-tuned. Mid-run loss spikes at lr 1e-1 and
3e-1 (e.g. 5.18, 6.01) recover under the cosine decay.

**(i) Caveats.** See Limits; the main ones: one model size (d=128), a 1 MB corpus in a 24.5-epoch regime where dense overfits
(gap +0.36) so quantisation partly acts as regularisation and val gaps may understate capacity costs (the train-side deficits above
are 1.5-2.1x the val-side ones; **hypothesis**), 2 seeds for the slow arms.
